**Audit date:** 2026-09-06

- **GB/T 38636-2020** 《信息安全技术 传输层密码协议》(TLCP) — primary target

## C-1 (Critical): ClientKeyExchange ECDHE body has a non-standard `uint16` length prefix

### Spec
GB/T 38636-2020 §6.4.1.6 inherits RFC 5246 §7.4.7 — the CKE body for ECDHE suites is just the ECParameters-wrapped ephemeral pub:

```text
struct {
    ECParameters    curve_params;     /* curve_type(1) + named_curve(2) */
    opaque          point<1..2^8-1>; /* 1-byte len + 65-byte SM2 point */
} ClientECDHParams;
```

No overall length prefix on the body — the handshake header's 24-bit `length` field already covers it.

### Code
`src/tlcp/messages/client_key_exchange.rs:90-108`:

```rust
let payload_len = self.key_exchange.len();
let body_len = 2 + payload_len;
let mut buf = Vec::with_capacity(4 + body_len);
buf.push(HandshakeType::ClientKeyExchange as u8);
buf.push((body_len >> 16) as u8);
buf.push((body_len >> 8) as u8);
buf.push(body_len as u8);
// 16-bit payload length prefix (matches GmSSL 2026-06+
buf.extend_from_slice(&(payload_len as u16).to_be_bytes());
buf.extend_from_slice(&self.key_exchange);
```

The code emits `[type(1)][length(3)][uint16_len(2)][ECParameters+point(69)]`, total = 75 bytes.

### Conformance check
| Step | Bytes | Per RFC 5246? |
|---|---|---|
| HS header | 4 | ✅ standard |
| `uint16 payload_len` | 2 | ❌ **non-standard** |
| `ECParameters` (curve_type + named_curve) | 3 | ✅ |
| `point_len` (1) + point (65) | 66 | ✅ |

The `uint16` prefix is an extra 2 bytes that is **not in RFC 5246 or GB/T 38636-2020**. The comment claims it "matches GmSSL 2026-06+ `tls_uint16array_to_bytes`" — meaning this was added to fix an earlier interop issue with GmSSL master.

### Wire-trace evidence
Captured in `interop/openhitls/wire-traces/ecdhe-with-mutual-auth.pcap`. openHiTLS's `ParseClientKxMsgEcdhe` (`openhitls/tls/handshake/parse/src/parse_client_key_exchange.c:49-59`) does:

```c
if (pkt->ctx->negotiatedInfo.version == HITLS_VERSION_TLCP_DTLCP11) {
    uint8_t minLen = sizeof(uint8_t) + sizeof(uint16_t) + sizeof(uint8_t);
    if (pkt->bufLen - *pkt->bufOffset < minLen) {
        return ParseErrorProcess(pkt->ctx, HITLS_PARSE_INVALID_MSG_LEN, BINLOG_ID16222,
            logStr, ALERT_DECODE_ERROR);
    }
    // Ignore the three bytes
    *pkt->bufOffset += sizeof(uint8_t) + sizeof(uint16_t);
}
uint8_t pubKeySize = 0;
ParseOneByteLengthField(pkt, &pubKeySize, &msg->data);
```

So openHiTLS skips 3 bytes (the first 2 bytes of gm-tlcp's non-standard `uint16` prefix plus the `curve_type` byte), then reads a 1-byte point length. Note that this skip length is exactly the size of the ECParameters envelope `[curve_type=0x03][named_curve=0x0029]` (3 bytes) — openHiTLS's parser was designed for the standard wire format and assumes those 3 bytes are ECParameters.

gm-tlcp's CKE body for ECDHE is
```
[uint16=0x0045=69][ECParameters: 0x03 0x00 0x29][point_len=0x41=65][point: 65 bytes]
```
= 71 bytes total.

After openHiTLS's skip, the cursor is at byte index 3 — the **high byte of `named_curve`** (value `0x00`, since `named_curve = 0x0029`). openHiTLS reads this byte as the 1-byte point length → `pubKeySize == 0` → `HITLS_PARSE_INVALID_MSG_LEN` → alert **Decode Error**.

(The earlier draft of this section misidentified the consumed byte as "the low byte of the `uint16` payload length"; that is incorrect — the `uint16` low byte is `0x45`, which is one of the 3 skipped bytes. The byte actually consumed as the point length is `0x00`, which happens to be the high byte of `named_curve`.)

### Impact
- gm-tlcp ↔ openHiTLS: **fails** (alert Decode Error)
- gm-tlcp ↔ GmSSL master: works (GmSSL accepts the prefix)
- gm-tlcp ↔ Tongsuo NTLS: untested, but Tongsuo also follows GmSSL conventions so likely works

### Recommended fix
Remove the `uint16` prefix from `to_bytes()` and the corresponding read in `from_body()`. Approximately 5 lines of code, symmetric encoder/decoder change. Verify against both GmSSL master (regression test) and openHiTLS (new interop test). If GmSSL master truly requires the prefix, then a runtime negotiation probe (probe-byte) or feature flag is needed instead — but the cleanest solution is to fix GmSSL to match.

## C-2 (Critical): ServerKeyExchange is required for **all** suites, including static ECC

### Spec
Per GB/T 38636-2020 §6.4.1.5 (inherited from RFC 5246 §7.4.3), ServerKeyExchange is sent by the server only when the negotiated suite requires additional key-exchange material — i.e. only for ECDHE suites. For static-ECC suites (E013, E053), the server sends `Certificate` followed directly by `ServerHelloDone`.

### Code
`src/tlcp/mod.rs:1449-1459`:

```rust
// Step 4: Read ServerKeyExchange
let (_ct, ske_payload) = read_plaintext_record(&mut io)
    .await
    .map_err(|e| TlcpError::HandshakeFailed(format!("read ServerKeyExchange: {}", e)))?;
let (ske_type, ske_body, _rem) = parse_handshake_message(&ske_payload)?;
if ske_type != HandshakeType::ServerKeyExchange {
    return Err(TlcpError::HandshakeFailed(format!(
        "Expected ServerKeyExchange, got {:?}",
        ske_type
    )));
}
```

This block is **unconditional** — every handshake expects an SKE. The server-side code at `src/tlcp/mod.rs:2184-2200` is similarly unconditional: it calls `TlcpServerKeyExchange::generate(...)` and writes the resulting SKE record regardless of whether the negotiated suite is ECDHE or static-ECC. (`src/tlcp/handshake/server.rs` does not contain SKE generation; the search-confirmation hint in the v1 draft was wrong.)

### Conformance check
| Suite | Should send SKE per spec? | gm-tlcp sends SKE? |
|---|---|---|
| ECDHE_SM4_CBC_SM3 (E011) | ✅ yes | ✅ yes |
| ECDHE_SM4_GCM_SM3 (E051) | ✅ yes | ✅ yes |
| **ECC_SM4_CBC_SM3 (E013)** | ❌ no | ✅ yes — **non-standard** |
| **ECC_SM4_GCM_SM3 (E053)** | ❌ no | ✅ yes — **non-standard** |

The comment at line 1453 acknowledges this implicitly: "GmSSL master 2026-06+ ... sets `client_certificate_verify = 1` for those suites by default" — i.e. GmSSL master itself always sends SKE for ECDHE, and apparently (per the always-emit behavior) also for static-ECC.

### Wire-trace evidence

Captured in `interop/openhitls/wire-traces/e013-static.pcap` (re-captured 2026-09-06 against `openhitls-srv` running `hitls s_server -tlcp` with the bundled SM2 dual certs):

```
4   0.000298 192.168.65.1 → 172.17.0.2   TLCP 116 Client Hello
6   0.010973   172.17.0.2 → 192.168.65.1 TLCP 1318 Server Hello, Certificate, Server Key Exchange, Server Hello Done
9   6.999821   172.17.0.2 → 192.168.65.1 TLCP 73  Alert (Level: Warning, Description: Close Notify)
```

So openHiTLS sends **4 records** for static-ECC E013: ServerHello, Certificate, SKE, SHD (no `CertificateRequest`). gm-tlcp's client output is just:

```
[client] connecting to 127.0.0.1:52197
[client] TCP connected
[client] offering suites: [[E0, 13]]
```

— it never prints `handshake OK!` or `handshake FAILED: ...`. The client is killed after 6 s; the server logs `TLS handshake failed: 0x20a0016` (`HITLS_REC_NORMAL_IO_EOF`) and then sends a `close_notify`.

Why the hang (not a printed error)? gm-tlcp's flow for the SKE-receiving path is:

1. Step 4 (`mod.rs:1449`): read SKE → reads openHiTLS's SKE OK
2. Step 5 (`mod.rs:1486-1493`): `verify_ske_signature(is_ecc_mode=true, ...)`. openHiTLS signs over `cr ‖ sr ‖ uint24(enc_cert_len) ‖ enc_cert` (see `HS_PrepareSignDataTlcp` at `openhitls/tls/handshake/common/src/hs_common.c:255-281`), which is exactly what gm-tlcp builds at `verify.rs:49-57`. **Verification succeeds.**
3. Step 5.5 (`mod.rs:1505-1529`): read the next record, expecting either CertificateRequest or ServerHelloDone. openHiTLS sent SHD next, so the `cr_type == HandshakeType::ServerHelloDone` branch at `mod.rs:1513-1526` runs: the SHD bytes are appended to the transcript and execution falls through. The comment at `mod.rs:1519-1525` explicitly admits: "We can't easily 'unread' the record; just fall through and re-fetch SHD as usual."
4. Step 6 (`mod.rs:1531-1533`): read the next record expecting SHD. The server has **no more bytes to send** (SHD was already consumed in step 5.5). `read_plaintext_record` blocks forever on the empty socket.

So the actual failure for static-ECC is **a hang at step 6**, not the ECParameters-prefix error I quoted in the first draft of this section. (The earlier draft confused the static-ECC flow with the ECDHE flow — `ecdhe.rs::from_bytes` IS reached in the ECDHE branch and WOULD produce `"ECDHE params have wrong ECParameters prefix"`, but that is the failure for E011/E051, not E013/E053.)

### Impact
- gm-tlcp ↔ openHiTLS static-ECC: **hangs** (step 6 reads EOF after the second SHD is missing)
- gm-tlcp ↔ GmSSL master static-ECC: works (GmSSL master always emits SKE AND CR for ECDHE, and the flow's "rare" branch at `mod.rs:1513-1526` never triggers — the comment at `mod.rs:1520-1522` notes "this branch is rare (gmSSL master always sends CR for ECDHE)")
- gm-tlcp ↔ Tongsuo NTLS static-ECC: untested

### Recommended fix
- **Option A (preferred):** Treat static-ECC suites (E013, E053) symmetrically to ECDHE in the handshake flow but skip the SKE step entirely for them. Concretely:
  - In `mod.rs::connect_with_certs`, branch on `suite.ecdhe` after reading the Certificate; only read the SKE record when `is_ecc_mode == false` (i.e. `suite.ecdhe == true`).
  - In the corresponding server path, only emit SKE when the negotiated suite is ECDHE.
  - Address the step-5.5 / step-6 ordering hazard by re-reading the SHD if it was already consumed (the comment at `mod.rs:1517-1525` already anticipates this).
- **Option B:** Keep gm-tlcp's current "always read SKE" behavior and submit a spec clarification issue to the GB/T 38636-2020 maintenance body documenting that GmSSL/Tongsuo/gm-tlcp always send SKE for static-ECC suites. Update the comment at `mod.rs:1453` accordingly.
- **Option C:** Document the limitation in a "Known interop" section and pin the "always SKE" behavior in interop tests.

## M-1 (Major): ClientHello / ServerHello SM2-ephemeral-public field bypasses the standard extension framing

### Spec
RFC 5246 §7.4.1.4 (ClientHello extensions) and §7.4.1.3 (ServerHello extensions) define:

```text
struct {
    ExtensionType extension_type;    /* 2 bytes */
    opaque extension_data<0..2^16-1>; /* length-prefixed */
} Extension;

struct {
    Extension extensions<0..2^16-1>;   /* 2-byte total length prefix */
} Extensions;
```

So every extension has a 2-byte type code + 2-byte length + data. A peer that sends a standard-format extension would have gm-tlcp's parser interpret the type code as the SM2-key length, and the subsequent bytes as key material.

### Code
`src/tlcp/messages/client_hello.rs:187-197`:

```rust
let sm2_ephemeral_public = if pos + 2 <= data.len() {
    let key_len = u16::from_be_bytes([data[pos], data[pos + 1]]) as usize;
    pos += 2;
    if pos + key_len <= data.len() {
        Some(data[pos..pos + key_len].to_vec())
    } else {
        None
    }
} else {
    None
};
```

`src/tlcp/messages/server_hello.rs:65-74`:

```rust
let sm2_ephemeral_public = if data.len() > offset + 3 + 2 {
    let ext_len = u16::from_be_bytes([data[offset + 3], data[offset + 4]]) as usize;
    if data.len() >= offset + 5 + ext_len {
        Some(data[offset + 5..offset + 5 + ext_len].to_vec())
    } else {
        None
    }
} else {
    None
};
```

Both parsers consume the standard `extensions_length` field as the SM2-key length, then read that many bytes — including the leading `extension_type(2)` and per-extension `extension_data_length(2)` — as if they were the SM2 public key. A peer that follows RFC 5246 and uses a real extension (say, `extended_master_secret`, type `0x0017`) would be interpreted by gm-tlcp as `key_len = 23` (the `extensions_length`) followed by `key = <23 bytes starting with the extension_type=0x0017>` — not a 65-byte uncompressed SM2 public key. This would not match the expected shape → silent parse failure (the field is just stored as `Some(<garbage>)` and never validated).

Note: `extensions_length = 0` (the no-extension case) is the only value gm-tlcp's parsers handle correctly — they return `Some(empty vec)` or `None` and proceed.

### Conformance check
- Standard extension framing: ❌ not followed
- TLCP spec silence on SM2 ephemeral pub extension: §6.4.1.1 / §6.4.1.2 do not define such a field. Looking at GmSSL master, this field is in fact **never used** — ClientHello and ServerHello exchange ephemeral keys via ServerKeyExchange/ClientKeyExchange messages, not via Hello extensions.

### Impact
- The field is **dead code** — no path through `connect_with_certs` ever sets `sm2_ephemeral_public` to `Some`. The SKE body carries the ephemeral key for ECDHE.
- A standard-extension peer would silently misparse.

### Recommended fix
Remove the `sm2_ephemeral_public` field from `TlcpClientHello` and `TlcpServerHello` entirely. This is dead code that creates interop ambiguity.

## M-2 (Major): ECDHE PMS derivation requires GmSSL-specific `x̂` transformation

### Spec
GB/T 32918.3-2016 §6.4.2 (full key agreement): the shared point `V = [t]Q_peer`, then `PMS = KDF(x_V || y_V || Z_A || Z_B, klen)` where:

```
t = (x_self_R_hat · r_self + k_self) mod n
```

with `x̂ = 2^127 + (x mod 2^127)` per the **GmSSL** implementation. The standard does **not** mandate this `x̂` transform — it specifies `t = (x_R · r + k) mod n` directly.

### Code
`src/tlcp/pms.rs:111-112`:

```rust
let local_x_hat = scalar_from_x_hat(&local_ephemeral_x)
    .map_err(|e| TlcpError::HandshakeFailed(e.to_string()))?;
```

and the helper at `src/tlcp/pms.rs:193-214` (paraphrased): `x̂ = 2^127 + (x mod 2^127)`.

### Impact
- gm-tlcp ↔ gm-tlcp: works (symmetric)
- gm-tlcp ↔ GmSSL master: works (GmSSL uses the same `x̂` transform)
- gm-tlcp ↔ Tongsuo NTLS: works (forked from GmSSL)
- gm-tlcp ↔ openHiTLS: works IF openHiTLS also implements the `x̂` transform
- gm-tlcp ↔ any TLCP peer that implements GB/T 32918.3 strictly (without `x̂`): **fails** (different PMS → different master_secret → bad Finished MAC)

### Recommended fix
Add a feature flag `TLCP_ECDHE_X_HAT_TRANSFORM = true` (default on for GmSSL interop). Add a regression test that validates PMS output against known-good GmSSL test vectors. Document the limitation in the connector-level doc comment.

## M-3 (Major): SM2 default user_id `1234567812345678` is hardcoded and not configurable per-call

### Spec
GB/T 32918.1-2016 §6.1: `Z = SM3(ENTL || ID || a || b || x_G || y_G || x_pubA || y_pubA)`. The `ID` is an "**identification number of the user**" that the spec allows to be **any** length up to 65,535 bytes.

### Code
- `examples/interop_client.rs:24`: `const DEFAULT_DISTID: &str = "1234567812345678";`
- `src/tlcp/mod.rs:1804`: `let default_user_id: &[u8] = b"1234567812345678";`
- `examples/interop_client.rs:68`: `.with_server_sign_key(sign_pub, DEFAULT_DISTID.to_string())`

The connector accepts `server_sign_distid` via `with_server_sign_key(pub, distid)` (line 1317 of `src/tlcp/mod.rs`), which is good. But the **client's own SM2 signing key** used for CertificateVerify also uses `GM_TLS_DEFAULT_ID` (line 1887 of `src/tlcp/mod.rs`), hardcoded inside the SKE sign path. **The client-side `GM_TLS_DEFAULT_ID` is not exposed via the connector API** — only the server-side `distid` is.

Furthermore, the **server-side static ECC encryption** path (`src/tlcp/pms.rs:51-72`) and the ECDHE `Z` derivation both hardcode `"1234567812345678"` instead of taking it from `server_sign_distid`. So the server's sign-cert `distid` and the server's enc-cert `distid` must be the same, but they are different certificates — semantically distinct entities that should be able to have different distids.

### Conformance check
| Where | Used | Configurable? |
|---|---|---|
| `server_sign_distid` | SKE signature verify (mod.rs:1471-1485) | ✅ via `with_server_sign_key` |
| ECDHE `Z_server` (mod.rs:1805) | PMS derivation | ❌ hardcoded `"1234567812345678"` |
| ECDHE `Z_client` (mod.rs:1807) | PMS derivation | ❌ hardcoded `"1234567812345678"` |
| Client CV signing (mod.rs:1887) | CV signature generation | ❌ hardcoded `GM_TLS_DEFAULT_ID` |

### Impact
- gm-tlcp ↔ GmSSL master / Tongsuo: works (all use `1234567812345678` as default)
- gm-tlcp ↔ any TLCP peer with a different default ID: **fails**

### Recommended fix
Make `distid` an explicit connector parameter and pass it through to all SM2 operations. The connector API should distinguish `server_sign_distid` and `server_enc_distid` (the encryption-cert distid is the one used for ECDHE `Z_server`).

## m-1 (Minor): ClientHello / ServerHello `random` does not start with 4-byte GMT Unix Time

### Spec
RFC 5246 §7.4.1.2: "The first 4 bytes represent the current time and date in standard UNIX 32-bit format (seconds since the midnight starting Jan 1, 1970, UTC, ignoring leap seconds) according to the sender's internal clock."

### Code
`src/tlcp/messages/client_hello.rs:48`: `rand_core::RngCore::fill_bytes(&mut rand_core::OsRng, &mut random);` — fills all 32 bytes with RNG output.

### Impact
- All real TLCP peers (GmSSL, Tongsuo, openHiTLS) use the same convention. RFC compliance: ❌. Interop: ✅.
- No security impact.

### Recommended fix
Low priority. Either fill the first 4 bytes with `SystemTime::now().duration_since(UNIX_EPOCH).as_secs() as u32` for spec compliance, or document the deviation.

## D-1 (Doc): `alert.rs` module comment is internally contradictory

### Code
`src/tlcp/alert.rs:6-13`:

```rust
//! Alerts carry a 1-byte level (`Warning` or `Fatal`) and a 1-byte
//! description code. The single wire-format record is exactly
//! `[level, description]` (2 bytes total) inside a HANDSHAKE-type
//! record (per GmSSL's `tls_send_alert`).
//!
//! GB/T 38636-2020 §6.4.5.2.1 specifies that the alert *record* uses
//! the HANDSHAKE content type, not the alert content type that some
//! other implementations expect. This is one of the spots where
//! early GmSSL versions had a wire-level bug; the current master
//! (`3.3.0-dev.1183+`) is correct.
```

The comment says "specifies HANDSHAKE content type" then "not the alert content type ... the current master is correct" — the "correct" interpretation depends on what the standard actually says. Per the actual code at `mod.rs:162` (`TLCP_RECORD_TYPE_ALERT: u8 = 0x15`), the standard uses Alert content type, and GmSSL master is correct.

### Recommended fix
Rewrite the comment to:


## D-2 (Doc): Module-level docs should call out the GmSSL-targeted design

### Issue
Many module doc comments include phrases like:
- "matches GmSSL 2026-06+ master"
- "matches GmSSL since commit `57c9433` (2026-06-01)"
- "matches GmSSL tls_uint16array_to_bytes format"
- "matches GmSSL convention"

This is fine for technical detail, but a top-level "Limitations" / "Interop boundaries" section at `src/tlcp/mod.rs:107-119` (currently "Interoperability") should explicitly enumerate:

1. **CKE wire format**: gm-tlcp emits a `uint16` length prefix that openHiTLS rejects (C-1).
2. **SKE always sent**: gm-tlcp expects SKE for static-ECC suites; standards-strict peers don't send SKE (C-2).
3. **ECDHE x̂ transform**: GmSSL-specific (M-2).
4. **SM2 distid**: hardcoded `"1234567812345678"` (M-3).

This helps consumers decide whether gm-tlcp fits their use case without reading every module's comments.

## What we did NOT audit

- **`gm_crypto` internals** (the SM2 / SM3 / SM4 implementations): out of scope. These are shared with the rest of the `gm-*` ecosystem and audited separately.
- **TLS record layer version handling for plaintext records**: `read_plaintext_record` (mod.rs:201-219) does **not** check the version field on plaintext records, only on encrypted ones. RFC 5246 §6.1 specifies legacy version `0x0301` for ClientHello plaintext records, but TLCP uses `0x0101` throughout. The behavior is consistent with TLCP practice; not flagged.
- **`connect_tlcp` / `accept_tlcp` / `TlcpEcdheContext`** (deprecated simulated handshakes): out of scope — these are explicitly marked deprecated and not production paths.
- **Session resumption** (`src/tlcp/session.rs`): implementation is straightforward (master_secret + randoms + cipher_suite cached). RFC 5246 §7.4.5 / GB/T 38636 §6.4 abort-of-session-resumption is followed but not exhaustively audited.
- **Alert protocol**: see D-1. The 16 codes defined in `src/tlcp/alert.rs:43-76` are a subset of RFC 5246 + TLCP extensions; missing codes include `decryption_failed`, `record_overflow`, etc. This is not strictly a defect — `from_bytes` rejects unknown codes via `Err(TlcpError::InvalidMessage)`, and the set covers the codes TLCP peers are observed to send.
- **Server-side cipher suite preference**: `src/tlcp/handshake/server.rs` always picks the first matching client-offered suite. Per RFC 5246 §7.4.1.2 the server SHOULD pick according to its own preference; gm-tlcp's behavior is a client simplification, not strictly a violation.

> **Audit v2 corrections (2026-09-06):** The v1 draft claimed the CBC padding format `N x N || N` violates RFC 5246 §6.2.3.2. The v1 M-2 / D-2 sections have been removed. Other line-reference and wording fixes were applied to C-2 and M-1.
