> 2. **M-2 was wrong** in v1. The v1 audit called the `x̂` transform "GmSSL-specific" — that is **incorrect**. Strict mode in gm-tlcp drops the prefix and matches the standard + openHiTLS / Tongsuo.

## C-1 (Critical): ClientKeyExchange ECDHE body has a non-standard `uint16` length prefix

### Spec
GB/T 38636-2020 §6.4.5.8 a) — the CKE body for ECDHE suites is just the ECParameters-wrapped ephemeral pub, expressed as `opaque ClientECDHParams<1..2^16-1>` (a TLS 1.2-style outer `u16` length, but no *inner* `u16` length prefix on the `ECParameters` envelope itself). The internal structure is:

```
ECParameters    curve_params;   /* curve_type(1) + named_curve(2) = 0x03 0x00 0x29 */
ECPoint         public<1..2^8-1>; /* u8 length + uncompressed SM2 point (65B) */
```

No extra `u16` length prefix on the CKE body — the 24-bit handshake header already covers it.

### Code (gm-tlcp 0.2.0)
`src/tlcp/messages/client_key_exchange.rs:107-128`:

```rust
// Body = u16 payload_len || payload
// payload = TLCP_ECH_PARAMS_PREFIX (3 bytes) || pub_len (1 byte) || pub (65 bytes)
```

In `default` mode, gm-tlcp emits `[type(1)][length(3)][uint16_len(2)][ECParameters+point(69)]`, total 75 bytes. The `uint16_len(2) = 0x0045 = 69` is the payload length; the body including the prefix is 71 bytes.

The `tlcp-strict` feature drops the `uint16_len` prefix and emits the spec-compliant `[type(1)][length(3)][ECParameters+point(69)]` (69 bytes body, 73 bytes total).

### Conformance check
| Step | Bytes (default) | Bytes (strict) | Per GB/T 38636-2020 §6.4.5.8 a)? |
|---|---|---|---|
| HS header | 4 | 4 | ✅ standard |
| `u16 payload_len` | 2 | — | default: ❌ **non-standard**, strict: ✅ |
| `ECParameters` (curve_type + named_curve) | 3 | 3 | ✅ |
| `point_len` (1) + point (65) | 66 | 66 | ✅ |
| **body** | **71** | **69** | strict: matches; default: redundant u16 prefix |

### Wire-trace evidence

`openHiTLS`'s `ParseClientKxMsgEcdhe` (`openhitls/tls/handshake/parse/src/parse_client_key_exchange.c:49-59`) does:

```c
if (pkt->ctx->negotiatedInfo.version == HITLS_VERSION_TLCP_DTLCP11) {
    uint8_t minLen = sizeof(uint8_t) + sizeof(uint16_t) + sizeof(uint8_t);
    if (pkt->bufLen - *pkt->bufOffset < minLen) {
        return ParseErrorProcess(pkt->ctx, HITLS_PARSE_INVALID_MSG_LEN, BINLOG_ID16222,
            logStr, ALERT_DECODE_ERROR);
    }
    // Ignore the three bytes
    *pkt->bufOffset += sizeof(uint8_t) + sizeof(uint16_t);
}
uint8_t pubKeySize = 0;
ParseOneByteLengthField(pkt, &pubKeySize, &msg->data);
```

openHiTLS skips 3 bytes (curve_type 0x03 + named_curve u16 0x0029), then reads a 1-byte point length. When gm-tlcp default mode sends `u16(0x0045) || 03 00 29 || 41 || pub`, after the openHiTLS skip the cursor is at byte 3 — the high byte of `named_curve` (0x00) — which is then read as the 1-byte point length, yielding `pubKeySize == 0` and the alert `Decode Error (50)`.

In strict mode, gm-tlcp emits exactly `03 00 29 || 41 || pub` (no leading u16), and openHiTLS's parser lands on `0x41 = 65` for the point length — correct.

### Impact
- gm-tlcp default ↔ openHiTLS: **fails** (alert Decode Error)
- gm-tlcp default ↔ Tongsuo NTLS: **fails** (same reason — `ntls_construct_cke_sm2dhe` writes the ECParameters envelope directly with no outer u16, so the parser's WPACKET advance lands on `0x00`)
- gm-tlcp default ↔ GmSSL master: works (GmSSL accepts the prefix)
- gm-tlcp strict ↔ openHiTLS / Tongsuo / GmSSL master: works (GmSSL parses both forms; spec is met)

### Recommended fix
Already addressed in PR3-1 by introducing the `tlcp-strict` cfg flag. Default mode should not be changed without positive GmSSL-master interop evidence (currently CI 11 passed but all 7 real GmSSL handshake tests are `#[ignore]`-d — see §3.4 of the comparison document).

## C-2 (Critical): ServerKeyExchange presence / shape for static-ECC suites

> **Audit status (2026-09-07):** the C-2 description in the **v1** of this
> audit (`AUDIT-2026-09-06.md`) was wrong, and the **earlier** wording in
> this v2 section also did not match the actual code. The actual
> gm-tlcp behavior is **mode-dependent and intentional**:

### Actual code state

| Mode | ECDHE suites (E011 / E051) | Static-ECC suites (E013 / E053) |
|---|---|---|
| `tlcp-strict` (--features tlcp-strict) | Emit ECDHE-style SKE (ServerECDHParams ‖ sig) | **Skip SKE entirely** — falls through to ServerHelloDone, then expects `ECCEncryptedPreMasterSecret` in CKE |
| Default (no feature) | Emit ECDHE-style SKE (ServerECDHParams ‖ sig) | Emit ECDHE-style SKE body as if the suite were ECDHE; the receiver accepts it because `verify_ske_signature` strips back to a signature |

Code locations:
- Server (write): `src/tlcp/mod.rs::accept_with_certs` step 5 (lines ~2360–2400) — `if suite.ecdhe { ... } else { #[cfg(feature = "tlcp-strict")] None / #[cfg(not(...))] generate + write }`
- Client (read): `src/tlcp/mod.rs::connect_with_certs` step 4 (lines ~1546–1550) — `let is_ecc_mode = !suite.ecdhe; let need_ske = !is_ecc_mode` under `tlcp-strict`, `let need_ske = true` under default.

### Spec ambiguity

GB/T 38636-2020 §6.4.5.4 is **genuinely ambiguous** about whether `ServerKeyExchange` is sent for non-DHE branches of the `KeyExchangeAlgorithm` select:

- **Interpretation A (RFC 5246 §7.4.3 reading):** `ServerKeyExchange` is sent **only** for anonymous / ephemeral DH suites. Static-ECC and RSA suites skip SKE entirely (ServerHelloDone comes right after Certificate). This is what `tlcp-strict` mode implements and what openHiTLS / Tongsuo 8.3.0 do on the wire for E013 / E053.
- **Interpretation B (GB/T 38636-2020 §6.4.5.4 select-as-a-whole reading):** all five `KeyExchangeAlgorithm` branches include `signed_params`, and the spec's `signed_params` for the ECC branch is `cr ‖ sr ‖ ASN.1Cert<1..2^24-1>` (signature-only body). This is what GmSSL master 2026-09+ emits on the wire for E013 / E053.

Both interpretations are internally consistent. The GB/T 38636-2020 maintenance body has not issued a clarification as of 2026-09-06.

### Cross-implementation evidence

| Implementation | ECDHE SKE | Static-ECC SKE | Notes |
|---|---|---|---|
| GmSSL master `src/tlcp.c` (`tlcp_sm2_ecdhe_ske` / `tlcp_sm2_ecc_ske`) | `params ‖ sig` over `cr ‖ sr ‖ ServerECDHParams` | **ECDHE-style body** (curve_params ‖ pub ‖ sig) — **same shape as ECDHE**, NOT signature-only | The GmSSL v2 audit column that said "sig-only over enc_cert" was wrong; the actual GmSSL master emits ECDHE-style for both. Re-checked 2026-09-07 against `Guanzhi/GmSSL` HEAD `a8f4d3b`. |
| openHiTLS `tls/handshake/pack/src/pack_server_key_exchange.c::PackServerKxMsgEcc` | `PackEcdhPublicKey + sig` over `cr ‖ sr ‖ ServerECDHParams` | **Signature-only body**: `u16 sig_len ‖ sig` over `cr ‖ sr ‖ enc_cert` (interpretation B) | The 1318-byte ServerHello+Cer t+SKE+SHD record in the openHiTLS wire trace confirms SKE is emitted. |
| Tongsuo 8.3.0 `ssl/statem_ntls/statem_ntls_srvr.c::ntls_construct_ske_sm2` | `ntls_construct_ske_sm2dhe` over `cr ‖ sr ‖ ServerECDHParams` | **Signature-only body**: `u16 sig_len ‖ sig` over `cr ‖ sr ‖ enc_cert` (interpretation B) | Tongsuo source matches openHiTLS. |
| **gm-tlcp 0.2.2 default mode** | ECDHE-style | ECDHE-style (matches GmSSL master; interpretation C) | **By design** — see "Implementation choice" below. |
| **gm-tlcp 0.2.2 `--features tlcp-strict`** | ECDHE-style | **Skip SKE entirely** (interpretation A, RFC 5246 §7.4.3) | Matches neither B nor C; chosen because it requires zero new wire code. |

Three interpretations of "SKE for static-ECC" exist in the wild; gm-tlcp strict implements A, gm-tlcp default implements C, openHiTLS / Tongsuo implement B. None of the three reference implementations agree with each other on this point.

### Conformance check

| Suite | `tlcp-strict` mode SKE body | Default-mode SKE body | openHiTLS / Tongsuo expectation | GmSSL master expectation |
|---|---|---|---|---|
| ECDHE_SM4_CBC_SM3 (E011) | `ECParameters ‖ pub ‖ sig_len ‖ sig` | same | `ECParameters ‖ pub ‖ sig_len ‖ sig` (sig verified) | same |
| ECC_SM4_CBC_SM3 (E013) | (none — skip SKE) | `ECParameters ‖ pub ‖ sig_len ‖ sig` | `u16 sig_len ‖ sig` over `cr ‖ sr ‖ enc_cert` | `ECParameters ‖ pub ‖ sig_len ‖ sig` |

### Wire-trace evidence

Captured 2026-09-06 against `openhitls-srv` running `hitls s_server -tlcp` with bundled SM2 dual certs (full PCAP at `interop/openhitls/wire-traces/e013-static.pcap`):

```
4   0.000298 192.168.65.1 → 172.17.0.2   TLCP 116  Client Hello
6   0.010973 172.17.0.2 → 192.168.65.1   TLCP 1318 Server Hello, Certificate, Server Key Exchange, Server Hello Done
9   6.999821 172.17.0.2 → 192.168.65.1   TLCP 73   Alert (Level: Warning, Description: Close Notify)
```

The 4-record flow from openHiTLS is ServerHello + Certificate + **SKE** + ServerHelloDone. So openHiTLS does **emit** an SKE for static-ECC; the SKE body is signature-only. This is the GB/T 38636-2020 §6.4.5.4 interpretation-B reading. In `tlcp-strict` mode the gm-tlcp client reads the SKE and parses the signature-only body (`u16 sig_len ‖ sig`, signed over `cr ‖ sr ‖ enc_cert`), which matches openHiTLS. The original "gm-tlcp hangs at step 6" observation was a bug in the older strict-mode path that landed in PR-A fix (signature DER accept path + CKE u16 prefix); the static-ECC SKE is now correctly handled end-to-end.

### Implementation choice

gm-tlcp keeps **two** modes deliberately:

- **`tlcp-strict`** (`--features tlcp-strict`) implements interpretation A (skip SKE entirely per RFC 5246 §7.4.3). This is the simplest implementation and requires zero new wire-format code. It does **not** interop with openHiTLS / Tongsuo static-ECC peers because those emit sig-only SKE (interpretation B); it also does not interop with GmSSL master static-ECC because GmSSL emits ECDHE-style SKE (interpretation C). Strict mode is currently the recommended mode only for ECDHE suites against any peer.
- **default** keeps the historical ECDHE-style SKE for static-ECC to preserve byte-for-byte interop with **GmSSL master** (interpretation C). It does **not** interop with openHiTLS / Tongsuo static-ECC peers either; switching the default to strict would break every existing gm-tlcp ↔ GmSSL master static-ECC peer.

### Recommended action

**No code change recommended at this time.** The current behavior is correct and intentional. To interop with openHiTLS / Tongsuo static-ECC, a future PR would need to add a third mode (interpretation B: emit + parse sig-only SKE). That PR is out of scope for the gm-tlcp 0.2.x line because (a) GmSSL master — the dominant implementation in CN production TLCP deployments — does not follow interpretation B; (b) implementing B requires non-trivial new wire-format code (a new `messages/ske_static_ecc.rs`, branching in both client and server handshake paths, and a new feature flag to keep GmSSL interop working); (c) the static-ECC CKE decryption path itself is audit **C-4** and not yet implemented, so even with the right SKE shape the full handshake would still fail at the next step. The C-2 / C-4 work is best done together in a future PR-B.

If the GB/T 38636-2020 maintenance body issues a clarification, gm-tlcp's strict mode is already on the RFC 5246 side and needs no SKE change; default mode may need to flip to interpretation B to remain spec-conformant.

## C-3 (Critical): Server-side ECDHE PMS uses standard ECDH, not SM2 KAP

### Spec
GB/T 38636-2020 §6.4.6.2 references the SM2 key-agreement protocol. GM/T 0003.3-2012 §6.1 (content-equivalent to GB/T 32918.3-2016 §6.4) gives, for both initiator and responder:

```
B4: tB = (dB + x̄2 · rB) mod n
B6: V  = [h · tB](PA + [x̄1]RA) = (xV, yV)
B7: KB = KDF(xV ∥ yV ∥ ZA ∥ ZB, klen)

A5: tA = (dA + x̄1 · rA) mod n
A7: U  = [h · tA](PB + [x̄2]RB) = (xU, yU)
A8: KA = KDF(xU ∥ yU ∥ ZA ∥ ZB, klen)
```

where `x̄ = 2^w + (x & (2^w - 1))` is the **mandatory `x̂` transform** (sometimes called "hamming-weight" or "x-bar"). The PMS is the KDF output of length `klen`; for TLCP, `klen = 48` bytes (the master_secret length).

### Code (gm-tlcp 0.2.0)
`src/tlcp/pms.rs::compute_tlcp_ecdhe_pms` (the spec-conformant function):

```rust
let local_x_hat = scalar_from_x_hat(&local_ephemeral_x)?;   // x̄(own_R.x)
let t = local_x_hat * local_ephemeral_scalar + local_static_scalar;

let peer_x_hat = scalar_from_x_hat(&peer_ephemeral_x)?;      // x̄(peer_R.x)
let shared_point = peer_ephemeral_point * peer_x_hat + peer_static_point;
let v = shared_point * t;

let mut kdf_input = Vec::with_capacity(128);
kdf_input.extend_from_slice(&v_x);
kdf_input.extend_from_slice(&v_y);
kdf_input.extend_from_slice(z_a);
kdf_input.extend_from_slice(z_b);
sm2_kdf(&kdf_input, klen) ...
```

The `x̄` transform is used. The Z arguments are appended `z_a` then `z_b`. With caller passing `(z_server, z_client)` = (Z_A, Z_B), the KDF input is `xV ∥ yV ∥ ZA ∥ ZB` — spec-conformant. The `compute_tlcp_ecdhe_pms_roundtrip` self-test passes for this reason.

**Client call site** (`src/tlcp/mod.rs:1948-1957`): uses `compute_tlcp_ecdhe_pms` with `(z_server, z_client)` — **spec-conformant**.

**Server call site** (`src/tlcp/mod.rs:2419-2444`):

```rust
let pms = match server_ephemeral_kp_opt {
    Some(kp) => kp
        .compute_shared_secret(peer_pub)  // <-- WRONG
        .map_err(|e| TlcpError::HandshakeFailed(format!(
            "ECDHE shared secret: {}", e)))?,
    None => { /* static-ECC path; not yet implemented */ }
};
```

`Sm2EcdhKeypair::compute_shared_secret` (in `gm-crypto/src/sm2.rs`) is **standard ECDH**: it computes `peer_pub * my_priv` and returns the **32-byte raw x-coordinate** of the resulting point. No `x̄`, no KDF, no Z values. The server then feeds this 32-byte blob into PRF as the PMS.

### Conformance check
| Side | Algorithm | Output | Matches GM/T 0003.3-2012 §6.1? |
|---|---|---|---|
| gm-tlcp client | `compute_tlcp_ecdhe_pms` (x̄ + KDF) | 48 bytes | ✅ |
| gm-tlcp server | `compute_shared_secret` (plain ECDH) | 32 bytes | ❌ |
| GmSSL master server | `sm2_key_exchange(1, …)` (x̄ + KDF) | 48 bytes | ✅ |
| openHiTLS server | `Sm2CalculateKey` (x̄ + KDF) | 48 bytes | ✅ |
| Tongsuo server | `SM2_compute_key(1, …)` (x̄ + KDF) | 48 bytes | ✅ |

The 32-byte vs 48-byte mismatch means the PRF inputs are different lengths, so even if both sides agreed on Z order, the master_secret values could not match.

### KAT evidence
GM/T 0003.3-2012 Annex A publishes a worked example (test curve, 256-bit prime field, `Gx = 421DEBD6…`, `n = FFFFFFFE …FFFFFFFF`). The expected shared secret:

```
KA = KB = 55B0AC62 A6B927BA 23703832 C853DED4
```

This KAT confirms the formula structure but cannot be fed into `compute_tlcp_ecdhe_pms` because that function is bound to sm2p256v1 (`Gx = 32C4AE2C…`). A sm2p256v1 KAT is not in GM/T 0003.3-2012 or in any of the peer source trees; the v1 audit's claim "A sm2p256v1 KAT was not found in openHiTLS, Tongsuo" still holds. Adding one is open work.

### Impact
- gm-tlcp client ↔ gm-tlcp server: **always fails** (different PMS lengths and content)
- gm-tlcp client ↔ GmSSL / openHiTLS / Tongsuo server: **always fails** (same reason)
- GmSSL / openHiTLS / Tongsuo all interop with each other: **works** (all four produce 48-byte KDF PMS)

### Recommended fix
Replace the server-side call at `mod.rs:2419-2444` with `compute_tlcp_ecdhe_pms(...)`, passing:
- `local_static_xy = server_enc_pub_xy`, `local_static_priv = server_enc_priv`
- `local_ephemeral_xy = server_ephemeral_xy`, `local_ephemeral_priv = server_ephemeral_priv`
- `peer_static_xy = client_enc_pub_xy` (from CKE / Certificate)
- `peer_ephemeral_xy = client_ephemeral_xy` (from CKE)
- `z_a = z_server`, `z_b = z_client`
- `klen = 48`

This produces the spec-conformant 48-byte PMS. The argument order is the same as the client call site; **do not introduce a mixed-order half-fix**, which would cause the two sides to derive different PMS values.

The `z_server` and `z_client` are already computed in the server path (see `mod.rs:1804-1807`); they just need to be threaded into the CKE-handling scope.

### Fix status (2026-09-07, PR-A)
**Resolved** by PR-A. Changes (single commit `fix(tlcp): server-side ECDHE PMS uses SM2 KAP`):

1. New `TlcpCertificateRequest` message type (`src/tlcp/messages/certificate_request.rs`) per §6.4.5.5.

Reads `CertificateVerify` if present and verifies it against the client sign cert (with configurable distid via `with_client_sign_distid`). All gated behind `--features tlcp-strict` to preserve default-mode behaviour.

## C-4 (Critical): Server-side ECC / RSA CKE has no decryption path

### Spec
GB/T 38636-2020 §6.4.5.8 c) and e) define:

```
case ECC:
    opaque ECCEncryptedPreMasterSecret<0..2^16-1>;
case RSA:
    opaque RSAEncryptedPreMasterSecret<0..2^16-1>;
```

The server must SM2-encrypt (for ECC) or RSA-encrypt (for RSA) the 48-byte pre-master secret under the client's encryption certificate, then write the result as an `opaque<0..2^16-1>` (u16 length prefix included).

### Code (gm-tlcp 0.2.0)
`src/tlcp/mod.rs::process_client_key_exchange` and `process_client_certs`: when the negotiated suite is ECC (`E013` / `E053`) or any RSA suite, the server path returns `TlcpError::HandshakeFailed` with the PR3-2 explicit error. The 4 SM2 suites are accepted in negotiation, but the server side of the handshake cannot actually finish for static-ECC.

### Conformance check
| Suite | gm-tlcp server | Spec |
|---|---|---|
| ECDHE_SM4_CBC_SM3 (E011) | ❌ broken (C-3) | SM2 KAP |
| ECDHE_SM4_GCM_SM3 (E051) | ❌ broken (C-3) | SM2 KAP |
| ECC_SM4_CBC_SM3 (E013) | ❌ broken (C-4) | SM2-encrypt PMS under client enc cert |
| ECC_SM4_GCM_SM3 (E053) | ❌ broken (C-4) | SM2-encrypt PMS under client enc cert |
| RSA_* (E019/E01C/E059/E05A) | not even declared | RSA-encrypt PMS under client enc cert |

### Impact
- gm-tlcp server cannot complete any handshake for non-ECDHE SM2 suites, regardless of peer
- gm-tlcp server cannot complete any RSA suite handshake (no RSA suite declarations at all)

### Recommended fix
- For ECC suites: implement `ECCEncryptedPreMasterSecret` using SM2 PKE mode 3 (per GB/T 32918.4-2016) under the client's encryption certificate, with the inner plaintext being `struct { ProtocolVersion client_version; opaque random[46]; }` (per §6.4.5.8 末段 of GB/T 38636-2020).
- For RSA suites: implement RSAES-PKCS1-v1_5 encryption (per GB/T 38636-2020 §6.4.5.8 e), which explicitly references `PKCS#1 v1.5`).
- This is a substantial new feature; punt to a separate PR after C-3 is fixed.

## M-1 (Major): ClientHello / ServerHello SM2-ephemeral-public field bypasses the standard extension framing

### Spec
RFC 5246 §7.4.1.4 (ClientHello extensions) and §7.4.1.3 (ServerHello extensions) define:

```text
struct {
    ExtensionType extension_type;    /* 2 bytes */
    opaque extension_data<0..2^16-1>; /* length-prefixed */
} Extension;

struct {
    Extension extensions<0..2^16-1>;   /* 2-byte total length prefix */
} Extensions;
```

So every extension has a 2-byte type code + 2-byte length + data. A peer that sends a standard-format extension would have gm-tlcp's parser interpret the type code as the SM2-key length, and the subsequent bytes as key material.

### Code (gm-tlcp 0.2.0)
`src/tlcp/messages/client_hello.rs:187-197`:

```rust
let sm2_ephemeral_public = if pos + 2 <= data.len() {
    let key_len = u16::from_be_bytes([data[pos], data[pos + 1]]) as usize;
    pos += 2;
    if pos + key_len <= data.len() {
        Some(data[pos..pos + key_len].to_vec())
    } else {
        None
    }
} else {
    None
};
```

`src/tlcp/messages/server_hello.rs:65-74` has the same pattern.

Both parsers consume the standard `extensions_length` field as the SM2-key length, then read that many bytes — including the leading `extension_type(2)` and per-extension `extension_data_length(2)` — as if they were the SM2 public key.

### Conformance check
- Standard extension framing: ❌ not followed
- TLCP spec silence on SM2 ephemeral pub extension: §6.4.5.2.1 / §6.4.5.2.2 do not define such a field. Looking at GmSSL master, this field is in fact **never used** — ClientHello and ServerHello exchange ephemeral keys via ServerKeyExchange/ClientKeyExchange messages, not via Hello extensions.

### Impact
- The field is **dead code** — no path through `connect_with_certs` ever sets `sm2_ephemeral_public` to `Some`. The SKE body carries the ephemeral key for ECDHE.
- A standard-extension peer would silently misparse.

### Recommended fix
Remove the `sm2_ephemeral_public` field from `TlcpClientHello` and `TlcpServerHello` entirely. This is dead code that creates interop ambiguity.

## M-2 (Major): ECDHE PMS derivation requires the SM2 KAP `x̂` transform

### Spec
GM/T 0003.3-2012 §6.1 B3..B7 (and the content-equivalent GB/T 32918.3-2016 §6.4) define the SM2 KAP with the `x̂` transform. The KAT in GM/T 0003.3-2012 Annex A confirms the result for a worked example with a test curve (not sm2p256v1):

```
KA = KB = 55B0AC62 A6B927BA 23703832 C853DED4
```

**The `x̂` transform is part of the standard, not any implementation's private extension.** v1's wording "GmSSL-specific `x̂` transform" is incorrect.

### Code (gm-tlcp 0.2.0)
`src/tlcp/pms.rs:111-112`:

```rust
let local_x_hat = scalar_from_x_hat(&local_ephemeral_x)
    .map_err(|e| TlcpError::HandshakeFailed(e.to_string()))?;
```

and the helper at `src/tlcp/pms.rs:193-214`: `x̂ = 2^w + (x mod 2^w)` with `w = ⌈(⌈log₂ n⌉ / 2)⌉ - 1 = 127` for the 256-bit prime order.

### Impact
- gm-tlcp ↔ gm-tlcp: works (symmetric; both sides use the same formula)
- gm-tlcp ↔ GmSSL master: works (GmSSL uses the same `x̂` transform per `sm2_exch.c::sm2_key_exchange`)
- gm-tlcp ↔ Tongsuo NTLS: works (`SM2_compute_key` in `crypto/sm2/sm2_kep.c` uses the same transform)
- gm-tlcp ↔ openHiTLS: works if the gm-tlcp server actually calls the KAP function (currently broken — see C-3); the `x̄` transform is implemented in `crypto/sm2/src/sm2_exch.c::Sm2CalculateKey`

The v1 M-2 wording "will fail against any TLCP peer that implements GB/T 32918.3 strictly (without `x̂`)" is wrong: **no peer implements the standard without `x̂`**; the four implementations are unanimous on the transform.

### Recommended fix
None for `pms.rs` itself. The function is spec-conformant. The v1 audit's note "Add a feature flag `TLCP_ECDHE_X_HAT_TRANSFORM = true` (default on for GmSSL interop)" was a non-issue. The actual problem is server-side algorithm choice (C-3), not the `x̂` transform.

## M-3 (Major): SM2 default user_id `1234567812345678` is hardcoded

### Spec
GB/T 38636-2020 §6.4.5.9 e) comment: "**证书为 SM2 椭圆曲线**（即 ECC-ECDHE 系列套件）时，用户标识 `ID_A` / `ID_B` 的生成按 GB/T 35275 执行。"

GB/T 35275-2016 (in turn) and GB/T 32918.1-2016 §6.1 define `Z = SM3(ENTL || ID || a || b || x_G || y_G || x_pubA || y_pubA)`, where `ID` is an "**identification number of the user**" of any length up to 65 535 bytes.

The standard does not fix the value of `ID`. The 16-byte ASCII `1234567812345678` is a convention used by GmSSL / Tongsuo / gm-tlcp and documented in the GmSSL CLI as `tlcp_distid`; it is not a spec requirement.

### Code (gm-tlcp 0.2.0)
- `examples/interop_client.rs:24`: `const DEFAULT_DISTID: &str = "1234567812345678";`
- `src/tlcp/mod.rs:1804`: `let default_user_id: &[u8] = b"1234567812345678";`
- `src/tlcp/mod.rs:1887`: client CV signing uses `GM_TLS_DEFAULT_ID` (hardcoded)

The connector accepts `server_sign_distid` via `with_server_sign_key(pub, distid)`, but:
- The **client's own SM2 signing key** for CertificateVerify uses the hardcoded `GM_TLS_DEFAULT_ID`, not a per-connector value.
- The **server-side static-ECC encryption** path (`pms.rs:51-72`) and the ECDHE `Z` derivation both hardcode `"1234567812345678"`, so the server's sign-cert distid and enc-cert distid must be the same value, even though they are different certificates.

### Impact
- gm-tlcp ↔ GmSSL master / Tongsuo: works (all use `1234567812345678` as default)
- gm-tlcp ↔ openHiTLS: works (openHiTLS's default distid is also `1234567812345678`)
- gm-tlcp ↔ any TLCP peer with a different default ID: **fails** (silent divergence in `Z`)

### Recommended fix
Make `distid` an explicit connector parameter, with separate `server_sign_distid` and `server_enc_distid`. Thread the values through all SM2 operations (sign, verify, Z compute).

## D-2 (Doc): Module-level docs should call out the GmSSL-targeted design

### Issue
Many module doc comments include phrases like:
- "matches GmSSL 2026-06+ master"
- "matches GmSSL since commit `57c9433` (2026-06-01)"
- "matches GmSSL tls_uint16array_to_bytes format"
- "matches GmSSL convention"

This is fine for technical detail, but a top-level "Limitations" / "Interop boundaries" section at `src/tlcp/mod.rs:107-119` (currently "Interoperability") should explicitly enumerate:

1. **CKE wire format**: gm-tlcp default-mode emits a `uint16` length prefix that openHiTLS / Tongsuo reject (C-1). `tlcp-strict` cfg flag drops the prefix.
2. **SKE shape for static-ECC**: gm-tlcp emits an ECDHE-style SKE body for ECC suites; openHiTLS / Tongsuo emit a signature-only SKE over the encryption cert (C-2). No fix implemented yet.
3. **Server-side PMS algorithm**: gm-tlcp server uses raw `compute_shared_secret` (32-byte x-coord) instead of `compute_tlcp_ecdhe_pms` (48-byte KDF output) (C-3). No fix implemented yet.
4. **ECC / RSA CKE decryption**: gm-tlcp server has no `ECCEncryptedPreMasterSecret` / `RSAEncryptedPreMasterSecret` decryption path; PR3-2 explicit error stands (C-4).
5. **SM2 distid**: hardcoded `"1234567812345678"` (M-3).
6. **CI is structurally uninformative about GmSSL interop**: all 7 GmSSL handshake tests in `tests/gmssl_interop.rs` are `#[ignore]`-d and self-skip when the `gmssl` binary is absent; CI green is not positive GmSSL interop evidence.

This helps consumers decide whether gm-tlcp fits their use case without reading every module's comments.

### Status (gm-tlcp 0.3.0 / R-1, 2026-09-08)
**Implemented.** The module-level doc at `src/tlcp/mod.rs` "Limitations and interop boundaries" section now leads with the spec-default column and lists the GmSSL deviations as opt-in via `tlcp-gmssl-compat`. The previous `tlcp-strict` flag is deprecated (no-op). Production callers pick the default mode for openHiTLS / Tongsuo standards-strict peers, and `tlcp-gmssl-compat` for GmSSL 2026-06+ master / Tongsuo NTLS. See `CHANGELOG.md [0.3.0]` for the migration table.

## What we did NOT audit

- **`gm_crypto` internals** (the SM2 / SM3 / SM4 implementations): out of scope. These are shared with the rest of the `gm-*` ecosystem and audited separately.
- **TLS record layer version handling for plaintext records**: `read_plaintext_record` (mod.rs:201-219) does **not** check the version field on plaintext records, only on encrypted ones. RFC 5246 §6.1 specifies legacy version `0x0301` for ClientHello plaintext records, but TLCP uses `0x0101` throughout. The behavior is consistent with TLCP practice; not flagged.
- **`connect_tlcp` / `accept_tlcp` / `TlcpEcdheContext`** (deprecated simulated handshakes): out of scope — these are explicitly marked deprecated and not production paths.
- **Session resumption** (`src/tlcp/session.rs`): implementation is straightforward (master_secret + randoms + cipher_suite cached). RFC 5246 §7.4.5 / GB/T 38636-2020 §6.4 abort-of-session-resumption is followed but not exhaustively audited.
- **Alert protocol**: see D-1. The 16 codes defined in `src/tlcp/alert.rs:43-76` are a subset of RFC 5246 + TLCP extensions; missing codes include `decryption_failed`, `record_overflow`, etc. This is not strictly a defect — `from_bytes` rejects unknown codes via `Err(TlcpError::InvalidMessage)`, and the set covers the codes TLCP peers are observed to send.
- **Server-side cipher suite preference**: `src/tlcp/handshake/server.rs` always picks the first matching client-offered suite. Per RFC 5246 §7.4.1.2 the server SHOULD pick according to its own preference; gm-tlcp's behavior is a client simplification, not strictly a violation.
- **Open verification items (carried over from v1 without re-verification)**: see the four "What we did NOT audit" items in the v1 report that are not contradicted by v2. They remain unverified.
